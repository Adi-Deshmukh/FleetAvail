1. The problem FleetAvail is solving

FleetAvail is a predictive-maintenance and fleet-readiness decision system.

The central question is not merely “will this engine fail?” It is: “Given the current condition of every aircraft, when should we maintain them, do we have the parts, and how will those decisions affect the number of aircraft available?”

A traditional monitoring screen gives measurements. FleetAvail tries to turn measurements into an operational chain:

Telemetry→ Preprocessing→ RUL+ Failure Risk+ Anomaly→ Health State→ Digital Twin→ Maintenance→ Spares→ Fleet Availability

Why this matters: a prediction is useful only when it changes a decision. FleetAvail is designed to connect machine-learning outputs to operational decisions instead of stopping at a model score.

3. The mental model of the codebase

Think of the repo as five layers:

Layer 1
Data + ML
C-MAPSS loading, features, sequences, RUL, risk and anomaly.
Layer 2
Runtime
Turns incoming API telemetry into model inputs and safely handles cold-start/fallback behavior.
Layer 3
State
Health Fusion + Digital Twin turn model outputs into operational asset state.
Layer 4
Decision
Maintenance plan → spare allocation → projected availability.
Layer 5
Interface
FastAPI REST/WebSocket + React/Vite dashboard + tests/CI.

Important architectural rule: the API layer does not directly know how to call XGBoost, TensorFlow or Isolation Forest. CMapssModelRuntime sits between FastAPI and model artifacts.

7. C-MAPSS data pipeline

C-MAPSS is NASA's turbofan engine degradation benchmark used here as the controlled reference dataset. The project currently focuses on FD001.

Expected files

data/raw/cmapss/FD001/
├── train.txt
├── test.txt
└── RUL_test.txt

What the raw row contains

ml/cmapss/data.py assigns these names:

unit_id
cycle
op_setting_1
op_setting_2
op_setting_3
sensor_1 ... sensor_21

That is 26 columns: 2 identifiers/time columns + 3 operating settings + 21 sensors.

How training RUL is generated

For a training engine, the last observed cycle is treated as the failure endpoint:

RUL(row) = maximum_cycle_for_that_engine - current_cycle

How test RUL is generated

The test trajectory does not itself contain the full failure endpoint, so the code uses the official RUL_test.txt terminal-life value for each engine:

test_RUL(row) = official_terminal_RUL + last_test_cycle - current_cycle

Why this is important: the target is constructed from the correct source for each split, instead of leaking a future test trajectory endpoint into training.

Leakage-safe principles implemented

  • Training scalers are fitted only on training data.
  • Temporal features are calculated independently inside each engine.
  • Sequence windows never cross engine boundaries.
  • Failure-risk model splitting is engine-aware, not random-row splitting.
  • Test evaluation uses held-out engine trajectories.
  • The RUL target is capped at 125 cycles during model fitting.

8. Feature engineering — making measurements useful for models

ml/cmapss/features.py turns raw columns into a richer representation.

Step 1 — clean

clean():

  • sorts by unit_id and cycle
  • replaces infinite values with missing values
  • fills sensor missing values using each engine's sensor median
  • uses a global median fallback if an engine's sensor median is unavailable

Step 2 — remove constant features

A constant feature never changes. It contains no variation and therefore provides little predictive information in this pipeline. drop_constant_features() learns the keep-list from training data and applies the same columns to test data.

Step 3 — temporal features

For each base feature the code creates:

Feature typeMeaning
feature_deltaCurrent value minus previous cycle value.
feature_ma55-cycle rolling mean.
feature_ma1010-cycle rolling mean.
feature_ma2020-cycle rolling mean.

Why? A raw value tells you “where the system is.” A delta/rolling mean begins to tell you “how it is changing.” Degradation is fundamentally a time-dependent phenomenon.

Step 4 — scaling

StandardScaler transforms each feature so the training distribution is centered/scaled. The scaler is fitted once on training features and later reused during prediction.

Key concept: the scaler is part of the model pipeline. A trained model expecting standardized inputs cannot be safely fed arbitrary raw values. That is why model metadata stores the feature columns and scaler reference.

9. Sequence windows — why “30 cycles” is a big deal

A time-series model should see a sequence, not just one isolated row.

With a 30-cycle window:

[cycle 1 ... cycle 30] → one training example
[cycle 2 ... cycle 31] → next training example
[cycle 3 ... cycle 32] → next training example

ml/cmapss/sequences.py creates those overlapping windows. It groups by engine first, so the last 10 cycles of engine 1 are never accidentally joined with the first 20 cycles of engine 2.

What the shapes mean

A temporal input is conceptually:

[samples, cycles, features]

For example, one inference window is:

[30 cycles, N engineered features]

The reusable TelemetrySequenceBuffer in ml/sequence_buffer.py provides a strict bounded-history abstraction. The current model runtime also maintains its own deque(maxlen=30) per (aircraft_id, component).

10. RUL models — the “how long do we have?” branch

10.1 HistGradientBoosting baseline

ml/cmapss/model.py uses HistGradientBoostingRegressor. It is a tree-based regression model that is fast enough to run comfortably on a typical student laptop.

Instead of passing the entire 30×N sequence directly, the baseline summarizes the window into four statistics for every feature:

last state
mean over window
standard deviation over window
start-to-end delta

So the model is still using temporal information, but in compressed form.

10.2 LSTM

LSTM means Long Short-Term Memory. It is a recurrent neural-network architecture designed to carry useful information through a sequence.

The implementation builds:

30-cycle sequence
   ↓
LSTM(96, return_sequences=True)
   ↓
LSTM(48)
   ↓
Dense(32, ReLU)
   ↓
Dropout
   ↓
Dense(1)
   ↓
RUL

10.3 TCN

TCN means Temporal Convolutional Network. Instead of recurrence, it uses causal 1D convolutions with dilation rates.

dilation 1 → 2 → 4 → 8
       ↓
causal temporal convolutions
       ↓
global pooling
       ↓
dense layers
       ↓
RUL

Training details

The temporal models use TensorFlow/Keras. The training helper compiles with Adam and Huber loss, uses early stopping and reduces the learning rate when validation loss stops improving.

Current FD001 benchmark recorded by the repo

ModelMAERMSE
HistGradientBoosting30.8345.10
LSTM32.4546.29
TCN33.5447.39

MAE is average absolute error. RMSE penalizes larger errors more strongly. For the current recorded comparison, the baseline has the lowest test MAE.

In the current CMapssModelRuntime, FLEETAVAIL_RUL_MODEL=auto selects the available RUL branch with the lowest validated test MAE when comparison metadata exists. Explicit values baseline, lstm and tcn are also supported.

11. Failure-risk model — the “could it fail soon?” branch

ml/cmapss/failure_risk.py treats failure prediction as a binary classification problem.

The label

For the default horizon of 30 cycles:

RUL <= 30 → failure_within_horizon = 1
RUL >  30 → failure_within_horizon = 0

This is different from RUL. RUL asks how much time remains?; the classifier asks are we inside the chosen failure-risk horizon?

Why engine-aware splitting?

The same engine produces many rows. Random row splitting could put cycle 10 of an engine in training and cycle 100 of that same engine in test. That is too easy a test because the model has effectively seen the same physical trajectory.

engine_aware_split() uses GroupShuffleSplit so complete engine trajectories are separated into training, calibration and holdout sets.

Why XGBoost?

XGBoost is gradient-boosted decision trees. It is strong on structured/tabular data, handles nonlinear feature relationships and is relatively practical for this pipeline.

Why probability calibration?

The raw classifier probability is not automatically a perfectly trustworthy probability. FleetAvail therefore takes the held-out calibration-set probabilities, converts them to logits, and fits a logistic sigmoid / Platt calibrator.

features
  ↓
XGBoost raw probability
  ↓
logit(raw probability)
  ↓
held-out LogisticRegression calibrator
  ↓
calibrated failure probability

The model also handles class imbalance with scale_pos_weight = negatives / positives.

12. Anomaly model — the “does this look unusual?” branch

ml/cmapss/anomaly.py uses Isolation Forest, an unsupervised anomaly-detection algorithm.

Why “unsupervised”?

The training path does not require a detailed anomaly label for every row. It learns what normal-ish operating behavior looks like and asks whether new behavior is isolated from that reference population.

Reference population

The current training script selects rows with:

RUL >= 125
or, if necessary, the highest-RUL portion of the training data

This is an approximation of a healthy reference population for this first prototype.

Score direction

Scikit-learn's raw score_samples is higher for more normal observations. FleetAvail negates it so the internal contract is easier to read: higher = more anomalous.

Threshold

The default calibrated threshold is the 99th percentile of normal-reference anomaly scores. The idea is to keep the false-positive reference region tight while still flagging unusual behavior.

14. Health Fusion — turning separate signals into one operational state

ml/health.py is intentionally independent of the ML model implementation. It accepts already-computed health, anomaly, risk, RUL, confidence and data quality.

Formal score

The final 0–100 score is:

health_score =
  100 × [ 0.50 × health
        + 0.25 × (1 - anomaly)
        + 0.25 × data_quality ]

Notice what is not directly inside this weighted score: failure probability and RUL. Those are primarily used for classification/urgency and reason codes. This separation is important when reading the code.

Operational levels

LevelTrigger examples
CRITICALfailure risk ≥ 0.85, or RUL ≤ 20, or anomaly ≥ 0.90, or health score < 35.
DEGRADEDfailure risk ≥ 0.60, or RUL ≤ 45, or anomaly ≥ 0.70, or health score < 55.
WATCHfailure risk ≥ 0.30, or RUL ≤ 90, or anomaly ≥ 0.45, or health score < 75.
NORMALNone of the above triggers.

Extra reason codes are appended when data quality < 0.80 or confidence < 0.60.

Why reason codes? A human operator needs more than “DEGRADED.” Codes such as ELEVATED_FAILURE_RISK, SHORT_RUL and HIGH_ANOMALY tell the operator why the state changed.

15. Digital Twin — persistent memory of the aircraft

digital_twin/state.py is the state ledger for each aircraft.

What the twin contains

AircraftTwin
├── aircraft_id
├── mission_status
├── location
├── components
│   ├── ENGINE
│   ├── HYDRAULIC
│   ├── ELECTRICAL
│   └── LANDING_GEAR
├── events[]
└── maintenance_due

Each ComponentState stores health, degradation, RUL, failure probability, anomaly score, confidence, data quality, lifecycle status and last update cycle.

Prediction event

Every successful prediction can create a PREDICTION_UPDATE event. Maintenance creates a MAINTENANCE event.

Why persistence?

Without a persistent twin, a prediction exists only as a response. With a twin, the application has memory of the asset state, so later decisions can reference what happened before.

Why atomic JSON?

The prototype wants to run without PostgreSQL or Redis. The store writes to a temporary file, flushes/syncs it, and atomically replaces the destination. This reduces the chance of leaving a half-written state file.

The current file is data/digital_twin_state.json and is intentionally ignored by Git because it is runtime state rather than source code.

Terminology note: this is a digital twin in the state/operational sense. It is not currently a 3D geometry model, physics simulator, or CFD replica.

16. Maintenance optimizer — turning risk into work

decision_engine/maintenance_optimizer.py is a deterministic planning layer. It does not train an ML model.

Inputs per candidate

  • aircraft ID
  • component
  • mission priority
  • failure probability
  • RUL
  • maintenance duration
  • required spare part
  • spare availability

Priority score

risk      = clamp(failure_probability, 0, 1)
urgency   = 1 / (1 + RUL)
mission   = clamp(mission_priority, 0.1, 2.0)
spare_bonus = +0.10 when stock exists, -0.05 otherwise

score = 0.65 × risk
      + 8.0 × urgency
      + 0.30 × mission
      + spare_bonus

Because urgency = 1/(1+RUL), smaller RUL means larger urgency.

Actions

ActionMeaning
GROUND_AND_MAINTAINVery urgent work; schedule immediately when capacity exists.
SCHEDULE_MAINTENANCEElevated risk/urgency, but not necessarily immediate grounding.
MONITORNo immediate maintenance trigger.
ORDER_SPARE_AND_HOLDWork is constrained because required inventory is unavailable.
DEFER_CAPACITYWork is urgent enough to want maintenance, but daily capacity is full.

Capacity constraint

The planner tracks daily maintenance hours across a configurable horizon. Default application settings are 7 days and 24 maintenance hours/day.

17. Spare allocation — the resource constraint

decision_engine/spares.py solves a smaller but extremely important problem: even if maintenance is the right decision, can we physically execute it?

Current demo inventory

Allocation logic

Requests are ranked so compatible requests come first, then higher priority, then higher delay cost. Available stock is decremented as each request is allocated.

A request can end in:

ALLOCATED_FULL
ALLOCATED_PARTIAL
WAITLIST_NO_COMPATIBLE_STOCK

Unmet quantity is the critical field for the availability layer. A maintenance task that has no compatible part should not magically count as feasible.

18. Fleet availability — the final operational number

decision_engine/fleet_availability.py converts aircraft states and feasible recovery plans into an availability projection.

Current availability

An aircraft counts as currently available when:

current_status == READY
AND
critical == False

Projected recovery

A blocked aircraft can be considered recoverable inside the horizon when:

spare_available
AND maintenance_day is inside horizon
AND maintenance_duration_hours > 0
AND maintenance_duration_hours <= 24

The result exposes:

  • current_available
  • current_availability_pct
  • projected_available
  • projected_availability_pct
  • current blocked aircraft
  • projected blocked aircraft
  • recovered aircraft

Business meaning: availability is not a direct ML output. It is a decision-layer output calculated after predictions, health, scheduling and spare feasibility have been considered.

19. Observability, provenance, audit and drift

ml/observability.py is the project's Phase C operational-hardening layer.

Input quality

The code checks required operating settings and sensors. Missing and invalid fields reduce a normalized quality score.

Local explanation

The explanation method is local_signal_attribution. It compares current sensor values against the recent history and reports the strongest standardized deviations plus decision reasons.

This is not SHAP and not causal attribution.

Input drift

The system can build a reference mean/std for a history window and flag features whose current value reaches a z-score of 3 or more.

Prediction drift

It also compares recent outputs. Large shifts in failure risk or RUL are flagged as prediction-output drift.

Audit records

Recent predictions store:

timestamp
aircraft/component/cycle
status
latency
telemetry quality
prediction fields
provenance
explanation
drift
error (when applicable)

The in-memory audit deque retains up to 500 records.

Latency

Recent inference latency is used to report last, mean and p95. p95 means the latency below which approximately 95% of recorded observations fall in the sorted sample used by this implementation.

20. WebSocket and telemetry simulation

WebSocket

/ws/telemetry?aircraft_id=AF-001 is an asynchronous stream. The dashboard connects to it and receives an event about once per second.

The backend pins the stream to one aircraft/component rather than mixing multiple aircraft into one plot. Operator-facing health/risk/anomaly values are lightly smoothed with an exponential-style update:

smoothed = previous + 0.20 × (current - previous)

The raw model outputs are also retained in the event so smoothing does not destroy the underlying inference result.

Telemetry source precedence

When FD001 test data exists locally, FleetService can replay actual C-MAPSS test trajectories. When it does not, it generates C-MAPSS-shaped synthetic telemetry.

simulator/telemetry.py

This small simulator creates demo engine values such as EGT, vibration and oil pressure from a degradation factor. It is useful for understanding the input contract, but it is not the trained NASA model.

Vite is the frontend development/build tool. React source code is not itself a browser-ready production bundle. npm run build creates frontend/dist.

Important deployment distinction: GitHub Pages can host static HTML/JavaScript, but it cannot execute the Python FastAPI service or hold the local model files. The /guide page is therefore a static teaching document. The live prediction API still needs a Python-capable backend.

24. One aircraft walkthrough — follow AF-003 mentally

Suppose AF-003 sends ENGINE telemetry.

Step 1 — request arrives

POST /api/predict

{
  "aircraft_id": "AF-003",
  "component": "ENGINE",
  "telemetry": {...}
}

Step 2 — runtime receives it

FleetService.predict() checks that the aircraft and component exist, determines the cycle, measures input quality and calls CMapssModelRuntime.predict().

Step 3 — the runtime adds the sample

The sample is normalized and appended to the (AF-003, ENGINE) history.

Step 4 — cold start or full window

With 1 sample, the runtime returns COLD_START. With 30 samples, it can construct the full model input window.

Step 5 — model branches run

30-cycle history
     ├──→ RUL model → RUL cycles
     ├──→ XGBoost   → failure probability
     └──→ IF        → anomaly score

Step 6 — health is fused

The aircraft component state gets the prediction signals. Health Fusion turns them into a deterministic 0–100 score and operational level.

Step 7 — the twin remembers it

The twin gets an updated ENGINE component and a PREDICTION_UPDATE event.

Step 8 — maintenance uses the state

The maintenance planner considers every aircraft/component candidate. AF-003's risk/RUL affects its priority.

Step 9 — spare feasibility

The planner asks for ENG-FLT. If the part is unavailable, the task may become ORDER_SPARE_AND_HOLD.

Step 10 — fleet availability

The availability layer decides how many aircraft are currently ready and how many blocked aircraft can feasibly recover inside the horizon.

That is the “product” of FleetAvail: a sensor observation has eventually become a fleet-level readiness consequence.

25. Cold start vs ready window — a concept you must understand

StateMeaningWhat FleetAvail does
COLD_STARTFewer than 30 sequential samples.Returns no full RUL/risk/anomaly result from the temporal window and exposes sample count/quality.
READYFull 30-cycle sequence exists and data is sufficiently complete.Runs the available model branches.
DEGRADED_DATAInference can run but input quality is below the preferred threshold.Returns the prediction with explicit quality metadata.
ERRORSomething failed during inference.Records the error and returns an API error rather than silently fabricating success.

Why this exists: time-series models need context. A single row can be valid data but invalid as a 30-cycle model input.

When a model is trained, FleetAvail saves more than weights.

ArtifactWhy it exists

Common failure mode: model code can be perfectly correct while inference is wrong because the training-time feature order, rolling-feature construction or scaler was not reproduced. That is why the runtime uses model metadata instead of “guessing” feature columns.

28. Glossary — deeper definitions of the major technical terms

API

Application Programming Interface. A defined way for one program to request data or actions from another. FleetAvail's FastAPI routes are its HTTP API.

Async / asynchronous

Code can wait for I/O without blocking the entire server thread in the same way a synchronous call would. The WebSocket route is asynchronous because it continuously sends events.

Artifact

A saved output of training, such as a model file, scaler or metadata file, that is later used for inference.

Calibration

A post-processing step that tries to make predicted probabilities better aligned with observed frequencies. Here it is implemented with a held-out logistic sigmoid/Platt model.

Classification

Predicting a discrete class, such as 0/1. FleetAvail uses classification for failure-within-horizon risk.

Confusion between RUL and failure risk

RUL is a remaining-time regression estimate. Failure risk is a probability for a chosen horizon. The two are related but not interchangeable.

Data leakage

Information crosses a train/test boundary in a way that gives the model unfair knowledge. FleetAvail specifically protects against it in scaling, grouping and sequence construction.

Digital Twin

A software state representation tied to a real-world asset. In this repo it includes state plus event history and persistence.

Drift

A change in input or output behavior compared with a reference. FleetAvail implements simple reference-window z-score checks and rolling output-shift checks.

Feature

A numeric input used by a model. A feature can be a raw sensor, an operating setting, a delta or a rolling statistic.

Feature engineering

The process of transforming raw data into representations that are easier for a model to use.

Gradient boosting

An ensemble method that builds many small decision trees sequentially, each improving on the errors of the previous ensemble. HistGradientBoosting and XGBoost are different implementations/families of this broader idea.

Horizon

A future window. In the failure-risk model, the default horizon is 30 cycles.

HGB

HistGradientBoosting, the baseline RUL regression model in this repository.

Isolation Forest

An anomaly-detection method that recursively isolates observations. Observations that are easier to isolate are considered more unusual.

JSON

A text data format commonly used for API responses, configuration and metadata.

JWT

Not currently part of FleetAvail's core flow. This is a common web term, included here only as context: JSON Web Token is a compact signed token used for identity/authorization.

LSTM

Long Short-Term Memory. A recurrent neural-network architecture with gates that help preserve or discard information across sequence steps.

MAE

Mean Absolute Error: average of absolute prediction errors. Lower is better for the RUL benchmark used here.

ML inference

Using a trained model to produce a prediction from new data.

MLOps

Practices around operating machine-learning systems: versioning, provenance, monitoring, validation, deployment and lifecycle management. FleetAvail's Phase C is an application-level slice of this idea.

Normalization vs scaling

Normalization here means mapping incoming telemetry into the expected C-MAPSS-shaped field structure. Scaling means numeric transformation using the fitted StandardScaler. They are different operations.

Operational state

A business-facing state such as READY, DEGRADED, MAINTENANCE or CRITICAL. It is derived from aircraft status plus fused engine health.

p95

The 95th percentile. It is often used to describe tail latency rather than only average latency.

Platt scaling

A sigmoid probability calibration technique. FleetAvail implements the idea using LogisticRegression on the logit of the raw classifier probability.

Prediction provider / model contract

An agreed interface for producing the signals the rest of the system consumes. It allows model implementations to change without rewriting every decision layer.

Regression

Predicting a continuous numeric quantity. RUL prediction is regression.

RUL

Remaining Useful Life. The estimated number of remaining operating cycles.

Scaler

An object fitted on training data that transforms raw feature magnitudes into the representation expected by the trained model.

Sequence

A time-ordered collection of observations. FleetAvail's core runtime window is 30 cycles.

TCN

Temporal Convolutional Network. A sequence model based on causal convolutions rather than recurrent state.

Telemetry

Measurements from a physical or simulated system captured over time.

Threshold

A cutoff used to convert a continuous value into an operational decision. Health levels and anomaly/failure decisions use thresholds.

Time series

Data whose order in time matters. Engine degradation is a time-series problem because current behavior depends on past behavior.

Train / calibration / test

Different data roles. Training fits model parameters; calibration adjusts probability behavior; test/holdout data measures performance on unseen trajectories.

Validation vs verification

Validation asks “does the system solve the intended problem?” Verification asks “does the implementation behave according to its contract?” The repo contains both kinds of evidence, although it remains a prototype.

WebSocket

A persistent bidirectional connection. Instead of repeatedly making new HTTP requests, the browser can keep one connection open and receive streaming updates.

z-score

A standardized distance from a reference mean: roughly (value − mean) / standard deviation. FleetAvail uses an absolute z-score threshold for simple drift detection.
